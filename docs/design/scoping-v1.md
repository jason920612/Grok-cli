# 開放問題範圍界定設計（Open-Problem Scoping v1）

> 狀態：草案（待 review）
> 日期：2026-06-11
> 依賴：subagents-v1.md（代理通道 = 看板）、project-memory.md（用戶程度記憶）

## 1. 目的與定位

當用戶的任務是**開放問題**（多種有效做法、沒有標準解、需求/目標未定）時，先進入一個 **Scoping（範圍界定）階段**再實作。核心是**兩個對話通道**，把「要什麼」與「怎麼做」分開：

- **用戶通道**：只問**概念層**的「要什麼」（最終目標、設計原則/優先序、過程偏好、約束），**依用戶技術程度校準語言**——不懂技術的用戶只用概念與比喻，不丟術語。一次問齊（front-load）。
- **代理通道**：技術細節的「怎麼做」用**代理間的問答**在看板上討論收斂，**不拿去煩用戶**。

最後綜合成**計劃書/設計文檔** → 用戶核准 → 寫計劃 → 開始做。**避免做到一半一直中斷問技術問題。**

這是把「偵測開放 → 概念澄清 → 設計文檔 → 核准後實作」這個工作流產品化。

## 2. 已定案的決策

| 項目 | 結論 | 理由 |
|---|---|---|
| 觸發 | **模型自動判定開放就進** scoping（不先問用戶要不要） | 自動性；用信心閾值防誤判 |
| 用戶程度 | **自動推斷 + 記憶**，且**跨領域分別校準**（backend/frontend/… 各記各的，§5） | 不增加負擔；同一人各領域程度不同 |
| 中途改計畫 | **影響分析 → 若動到已完成則提醒重構 → 用戶堅持則用問題重新對齊**（§9.2） | 變更要看代價、要對齊，不盲改 |
| 技術 Q&A | **多代理看板討論**（design-analyst 子代理 proposer/critic 收斂） | 符合「代理間」；多角度辯論 |
| 適用 | 互動 REPL 模式（一次性 CLI 無法問用戶） | 需要問用戶 |
| 產出 | 設計文檔/計劃書優先，核准後才實作 | 一致工作流 |

## 3. 流程總覽

```
互動任務進來
  │
  ├─ 分流（Triage）：判斷 開放度 + 用戶技術程度（§4/§5）
  │
  ├─ 封閉 / 有標準解 / 信心不足以判開放 → 直接做（必要時邊做邊用合理預設）
  │
  └─ 高信心開放 → Scoping 階段
       ├─ 【用戶通道】批次概念問題（§6，校準 altitude）→ 收集 要什麼
       ├─ 【代理通道】看板技術 Q&A（§7，design-analyst 子代理）→ 決定 怎麼做
       ├─ 綜合 → 計劃書/設計文檔（§8）→ 概念層摘要給用戶
       └─ 用戶說「做」→ 寫最終計劃 → 實作（單代理 or 多代理編排）
            實作中：技術疑問走代理通道/合理預設，不中斷用戶（§9）
```

## 4. 開放度判斷（Triage）

任務開頭一個分類步（模型推理，非工具）：
- **封閉**：需求明確、有公認標準做法 → 直接做。
- **開放**：訊號包含——目標含糊（「做得更好」「加個功能」無細節）、本質是設計問題（「X 該怎麼架構」）、多個有意義權衡的架構選項、沒有明顯標準。
- **信心閾值**：**只有高信心開放才自動進 scoping**；模糊/邊界 → 直接做 + 明說假設（寧可少問，避免對封閉任務誤判而煩用戶）。

## 5. 用戶技術程度校準（跨領域分別校準）

- **分領域追蹤**：用戶程度按**領域**分別記（如 backend / frontend / database / ML / devops / build…），**非單一整體**——同一人可能後端是 expert、前端是 novice。任務碰到哪個領域，就用**該領域**的程度校準提問 altitude；一個任務跨多領域時，各部分各自校準。
- **自動推斷**：從對話中該領域的線索——用詞、具體度、描述「要什麼」vs「怎麼做」、問的問題類型。新領域起手中性。
- **存記憶**：寫進 user 類記憶，**key 為領域**（project-memory.md），跨對話一致；用戶一句話即可修正（「我其實懂後端」）。
- **光譜非二元**：每領域 novice / intermediate / expert。
- **持續校準**：更多訊號就更新**對應領域**的程度。

## 6. 用戶通道（概念提問）

- **只問「要什麼」**，永不問技術實作細節：
  - 最終目標 / 成功長怎樣
  - 設計原則與優先序（最在意什麼：速度？簡單？可擴充？成本？）
  - 過程偏好（要多參與？對做法有偏好或禁忌？）
  - 硬約束
- **altitude 校準**：
  - 不懂技術 → 概念 + **比喻**（例：「你要的是快速草稿，還是精修藍圖？」），不丟術語。
  - 懂技術 → 可精確、可帶選項。
- **批次 front-load**：一輪（或極少輪）結構化提問問齊，**不滴漏**。用結構化多選提問（類 AskUserQuestion 的產品工具，§10）。

## 7. 代理通道（技術 Q&A，多代理看板）

把用戶的概念答案**翻譯**成技術決策，在看板上由代理間問答收斂：
1. 主代理開一個 **design issue**，附用戶的目標/原則。
2. 生 **design-analyst 子代理**：可用 **proposer + critic** 兩角（或 N 個各提一案）。
3. 在 comment 串上 **Q&A 辯論**：proposer 提技術方案；critic 挑漏洞、問釐清；互相問答收斂到「最適合用戶需求」的具體技術實現。
4. 產出**技術實現計劃**——全程不浮到用戶。
- 複用 subagents-v1 的看板（issue/comment）；技術討論天然就是代理協作。
- 成本控制：只對**真正有多個有意義權衡**的技術點開辯論；單純的點主代理自己定（混合策略）。

## 8. 綜合 → 計劃書 → 核准

- 主代理綜合：用戶通道（目標/原則）+ 代理通道（技術方案）→ **設計文檔/計劃書**（如本 repo 的 docs/design/*）。
- 給用戶看的是**概念層摘要 + 關鍵決策**（依其 altitude），不是整份技術細節——讓用戶能在高層抓到方向性錯誤。
- 用戶核准（「做吧」）→ 寫最終計劃（持久化）→ 進實作（單代理 or §subagents 多代理）。

## 9. 避免中途中斷與中途改計畫

### 9.1 避免中途丟技術問題（核心要求）
- **front-load**：能在 scoping 解決的都先解決。
- **實作中的紀律**：技術疑問 → 代理通道 / 合理預設，**不丟給用戶**。只有**真正的需求歧義**（非技術細節、會改變結果）才升級給用戶，且**批次 + 概念層**。
- 這靠「兩通道架構 + prompt 紀律」共同保證。

### 9.2 用戶中途改計畫（變更需求）
用戶在 scoping 或**實作中途**提出變更/新需求時，固定走這個流程：

1. **影響分析（先做）**：模型分析變更**會不會影響已經做好的部分**——對照已關 issue / 已 merge 的 PR / 整合分支上的成果，以及進行中的工作。
2. **若影響已完成的東西 → 提醒重構**：用**用戶該領域的 altitude** 說明「這個改動會需要重做/重構已經做好的 X」+ 大致代價（不懂技術的用戶用概念/比喻講代價），請用戶確認是否要付這個重構成本。
3. **用戶堅持 → 重新對齊**：用問題與用戶**對齊新需求**（重新 scope 受影響的部分），更新計劃（開新的/修改 issues），再繼續——必要時 spawn 重構代理，在新分支上做 forward 重構並 merge。
4. **若不影響已完成**（只動還沒做的）：直接更新計劃 + 繼續，需要時用問題對齊。

實作面：已完成的工作在整合分支/已 merge 的 PR 上。重構是**向前做新工作**（新 issue/PR 改既有檔，read-before-write + snapshot 各自生效），不是自動 git revert——保留已完成的歷史，由代理重構覆蓋。

## 10. 工具與接點

| 元件 | 說明 |
|---|---|
| `ask_user`（新工具） | 互動 REPL 裡批次問用戶概念問題（題目可帶選項 + altitude）。回傳答案。僅互動模式。 |
| Triage / 校準 | 主代理內部推理步（非工具）；程度寫入 `remember`（user 類記憶）。 |
| 代理通道 | 複用 subagents-v1 看板：open_issue(design) + spawn design-analyst + comment Q&A。 |
| 計劃書 | 寫設計文檔（apply_patch 到 docs/ 或 plan 檔）。 |
| 模式 | 一次性 CLI 若遇開放+未定 → 退化為「best-effort + 明說假設」或提示改互動模式。 |

## 11. 風險與取捨

- **誤判開放度**：對封閉任務誤進 scoping 會煩人。對策：高信心閾值、邊界從寬（寧可直接做+說假設）。
- **程度校準錯**：對懂的人講太淺、對不懂的人講太深。對策：記憶 + 一句話可修；起手中性。
- **過度提問**：違背初衷。對策：批次、只問會改變結果的決策。
- **代理通道成本**：多代理設計辯論較貴。對策：只對真有權衡的技術點開辯論（混合）。
- **代理替不懂的用戶定技術**：本就是設計目的；用戶靠概念層摘要把方向、技術正確性交給代理。

## 12. 與既有的關係 / 復用

- **subagents-v1 看板** → 代理通道（技術 Q&A）。
- **project-memory** → 用戶程度與偏好的跨對話記憶。
- **設計文檔工作流** → 計劃書產出。
- **plan-mode 概念**：scoping 本質是一個「先規劃、核准才動手」的階段。

## 13. 實作階段（待 review 後）

```
階段 0 — Triage + 校準
  開放度分類 + 用戶程度推斷的 prompt/判準；程度寫入記憶。
  測試：plumbing（給定描述 → open/closed 標記；記憶讀寫）。
階段 1 — 用戶通道
  ask_user 工具（REPL 批次概念提問 + altitude）；不懂時用比喻的 prompt 紀律。
階段 2 — 代理通道
  design issue + design-analyst（proposer/critic）看板 Q&A 收斂技術方案。
階段 3 — 綜合 + 接線
  綜合計劃書 → 概念摘要核准 → 接 §subagents/單代理實作；中斷紀律。
階段 4 — 中途改計畫（§9.2）
  變更影響分析（對照已關 issue / 已 merge PR）→ 重構代價提醒 → 重新對齊 → forward 重構。
```

## 14. 本次不做（記錄）
- 一次性 CLI 的非互動澄清（先只做互動）。
- 變更時的**自動 git revert/回溯**已完成工作——本設計用 forward 重構（§9.2），不做自動回滾。
